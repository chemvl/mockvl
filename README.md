# mockvl

**Mock servers from your API schema.** Upload an OpenAPI or Postman file, or point mockvl at its URL, and you get a live mock URL that answers with your examples. Powered by [Stoplight Prism](https://github.com/stoplightio/prism). Accepts OpenAPI 3.x and Postman v2, in JSON or YAML.

- **Hosted mocks**: each mock is served at `https://<host>/m/<workspace>/<mock>/…`. Use the `Prefer` header to pick a status code or example, or to switch on dynamic data.
- **Workspaces and teams**: every user gets a personal workspace on first sign-in. You can invite members with the Owner, Admin, Editor or Viewer role.
- **Versions**: replacing a schema creates a new version. You can resync a URL-imported schema or restore any of the last 20 versions.
- **Custom responses**: you can override the generated body for any endpoint and status code. The in-app request preview calls the mock from the browser.
- **Per-mock settings**: request validation (422), CORS, and pause/resume.
- **Usage**: request counts per workspace over 7 or 30 days.
- **MCP server**: AI agents (Claude Code, etc.) can list mocks and change their responses using personal access tokens.
- **Admin dashboard**: an Ant Design back office, generated from a server-side resource registry.

## Tech stack

| Part | Stack |
| --- | --- |
| API (`apps/api`) | [Bun](https://bun.sh), [Hono](https://hono.dev) + `@hono/zod-openapi`, Drizzle ORM on PostgreSQL 16, Redis 7 (cache + rate limits), [pg-boss](https://github.com/timgit/pg-boss) jobs, Stoplight Prism |
| App (`apps/ui`) | Vite, React 19, React Router 7, TanStack Query, CodeMirror, client generated from the API's OpenAPI spec |
| Admin (`apps/admin`) | Vite, React 19, Ant Design 6 + ProComponents, headless Refine |
| Docs (`apps/docs`) | Small Bun static-site generator (`marked` + `shiki`) |
| Shared (`packages/*`) | Zod schemas (the API contract), shared tsconfig + Biome config |

## Prerequisites

- [Bun](https://bun.sh) 1.4 or newer
- Docker (with Compose) for local Postgres and Redis
- A Google Cloud OAuth 2.0 client of type **Web application**. Sign-in is Google-only, both in the app and in the admin dashboard.
- For the admin dashboard: a Google Workspace domain. Only accounts in `GOOGLE_ALLOWED_HD` can sign in to the admin dashboard.

## Install

```sh
git clone https://github.com/<owner>/mockvl.git
cd mockvl
bun install
```

One `bun install` at the root installs every workspace (`apps/*`, `packages/*`).

## Run locally

| Service | URL |
| --- | --- |
| API (+ mocks under `/m`) | http://localhost:3000 — interactive reference at http://localhost:3000/api/docs |
| App | http://localhost:5173 |
| Admin | http://localhost:8000 |
| Docs | http://localhost:4000 |
| Postgres / Redis (compose) | `localhost:5433` / `localhost:6380` |

**1. Start Postgres and Redis**

```sh
docker compose up -d
```

The compose services use host ports 5433 and 6380, so they don't collide with a natively installed Postgres or Redis.

**2. Configure Google OAuth.** In the Google Cloud console, open your OAuth client and add:

- Authorized JavaScript origins: `http://localhost:5173` (the app uses the popup sign-in flow)
- Authorized redirect URIs: `http://localhost:3000/api/admin/auth/google/callback` (admin sign-in)

**3. Configure the API**

```sh
cp .env.example .env
```

Fill in the required values. The API validates every variable at boot and refuses to start if one is missing or invalid.

| Variable | Value |
| --- | --- |
| `JWT_SECRET`, `ADMIN_SESSION_SECRET` | 32+ characters each: `openssl rand -hex 32` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | from your OAuth client |
| `GOOGLE_ALLOWED_HD` | your Google Workspace domain (admin sign-in) |
| `ADMIN_SEED_OWNER_EMAIL` | optional: your email, so your first admin sign-in becomes `owner` |
| `APP_GOOGLE_ALLOWED_HD` | optional: restricts app sign-in to one Workspace domain (unset means any Google account) |

The defaults already point at the compose databases and the local ports above. Email defaults to log-only: welcome and invite emails are written to the API log. Set `EMAIL_PROVIDER` to `resend` or `smtp` to deliver real email.

**4. Migrate and start the API**

```sh
bun run db:migrate
bun run dev            # watch mode; background workers run in-process
```

**5. Start the app**

```sh
cp apps/ui/.env.example apps/ui/.env     # set VITE_GOOGLE_CLIENT_ID (same as GOOGLE_CLIENT_ID)
bun run --cwd apps/ui dev
```

Open http://localhost:5173 and sign in with Google. You land in your personal workspace; create a mock from a schema file or URL there. The Vite dev server proxies `/api` and `/m` to the API.

**6. Optional: admin dashboard and docs**

```sh
cp apps/admin/.env.example apps/admin/.env
bun run --cwd apps/admin dev   # http://localhost:8000
bun run docs:dev               # http://localhost:4000
```

## Using mocks

Each mock is served without authentication at `{MOCK_PUBLIC_BASE_URL}/{workspace}/{mock}/<path>`. By default that is `{APP_URL}/m/...`.

```sh
curl http://localhost:5173/m/my-workspace/petstore/pets/1
curl http://localhost:5173/m/my-workspace/petstore/pets -H 'Prefer: code=404'
curl http://localhost:5173/m/my-workspace/petstore/pets -H 'Prefer: example=empty, dynamic=true'
```

- `Prefer: code=…, example=…, dynamic=true, seed=…` picks the response. The query params `__code`, `__example`, `__dynamic` and `__seed` do the same thing.
- The spec's `security` requirements are not enforced. Send `Prefer: code=401` to get the spec's 401 response.
- Request validation (422) and CORS are per-mock settings. A paused mock answers 503.
- **Limits:**
  - Schemas are capped at 5 MB and 1,000 operations.
  - A workspace can hold up to 50 mocks; each mock keeps its newest 20 versions.
  - 600 requests per minute per client IP per mock (`MOCK_RATE_LIMIT_PER_MINUTE`).
- **Rejected imports:** external `$ref`s are rejected. URL imports must use `https://`. URLs that resolve to private, loopback or link-local addresses are blocked.

## MCP for AI agents

The API serves a stateless Streamable HTTP MCP server at `{API_BASE_PATH}/mcp` (locally `http://localhost:3000/api/mcp`). Create a token on the workspace's **Access tokens** page. The token is shown only once, together with a ready-made config:

```json
{
  "mcpServers": {
    "mockvl": {
      "type": "http",
      "url": "http://localhost:3000/api/mcp",
      "headers": { "Authorization": "Bearer <token>" }
    }
  }
}
```

```sh
claude mcp add --transport http mockvl http://localhost:3000/api/mcp --header "Authorization: Bearer <token>"
```

| Tool | Access | Purpose |
| --- | --- | --- |
| `list_mocks` | read | Mocks in the token's workspace (slug, URL, status) |
| `list_mock_endpoints` | read | One mock's endpoints, their status codes, and which ones have a custom response |
| `update_mock_response` | write | Save a custom JSON body (≤ 256 KB) for one endpoint and status code |
| `reset_mock_response` | write | Restore the schema-generated response |

How tokens work:

- **Scope and lifetime:** a token belongs to one workspace and expires after 7, 30, 90 or 365 days. Only its SHA-256 hash is stored.
- **Write access:** write tools work only while the token owner's role is Owner, Admin or Editor.
- **Revocation:** revoking a token, or removing its owner from the workspace, takes effect on the next request.
- **Browsers are refused:** requests with an `Origin` header get 403. Use a desktop or CLI agent.

## Deploy

A production deployment has five parts:

- the **API container**: the `Dockerfile` in this repo; it also serves the mocks
- two **static builds**: the app and the admin dashboard
- **PostgreSQL 16**
- **Redis 7.0 or newer** (the rate-limit store needs `PEXPIRE … NX`)
- a **reverse proxy** that puts everything on one domain

The app calls `/api` on its own origin, so the proxy must serve the API and the app from the same host.

| Path on `https://mockvl.example.com` | Served by |
| --- | --- |
| `/api/*`, `/m/*` | API container (port 3000) |
| `/admin/*` | `apps/admin/dist` (SPA fallback to `/admin/index.html`) |
| `/*` | `apps/ui/dist` (SPA fallback to `/index.html`) |

### 1. Build and run the API image

```sh
docker build -t mockvl-api .
docker run -d --name mockvl-api -p 3000:3000 --env-file .env.production mockvl-api
```

The image runs as a non-root user and starts `bun run src/index.ts`, which runs the HTTP server and the background workers. To scale workers separately, run extra containers from the same image with `bun run src/worker.ts` as the command. pg-boss delivers each job to exactly one worker.

Production `.env.production`: start from `.env.example`, then set:

```sh
NODE_ENV=production
DATABASE_URL=postgres://user:pass@db-host:5432/mockvl
REDIS_URL=redis://redis-host:6379
APP_URL=https://mockvl.example.com
API_URL=https://mockvl.example.com/api
ADMIN_URL=https://mockvl.example.com/admin
TRUST_PROXY=true        # behind the reverse proxy: read the client IP from X-Real-IP / X-Forwarded-For
DOCS_ENABLED=false      # hide /api/docs and /api/openapi.json in production
# Also set: JWT_SECRET, ADMIN_SESSION_SECRET, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_ALLOWED_HD,
# and an email provider (EMAIL_PROVIDER=resend|smtp + its keys) for real welcome/invite emails.
```

Health checks: `GET /api/health` (liveness) and `GET /api/ready` (pings Postgres and Redis; returns 503 when either is down).

### 2. Run database migrations

The runtime image ships production dependencies only, and `drizzle-kit` is a dev dependency. So run migrations before each release from a checkout of the deployed commit, with a root `.env` that holds the production values:

```sh
bun install
bun run db:migrate
```

Never point migrations at a read replica (`DATABASE_REPLICA_URL`).

### 3. Build the app and the admin dashboard

```sh
# App → apps/ui/dist (served at /)
VITE_BASE_URL_PUBLIC=/ VITE_GOOGLE_CLIENT_ID=<client-id> bun run --cwd apps/ui build

# Admin → apps/admin/dist (served at /admin/); apps/admin/.env.example already
# sets VITE_BASE_URL_PUBLIC=/admin/, VITE_ROUTER_BASENAME=/admin, VITE_ADMIN_API_URL=/api
cp apps/admin/.env.example apps/admin/.env
bun run --cwd apps/admin build
```

`VITE_BASE_URL_PUBLIC` is required for the app build. Vite values are baked in at build time, so rebuild after changing them.

### 4. Configure the reverse proxy

Example nginx server block. Copy `apps/ui/dist` to `/srv/mockvl/ui` and `apps/admin/dist` to `/srv/mockvl/admin`.

```nginx
server {
  listen 443 ssl;
  server_name mockvl.example.com;
  # ssl_certificate / ssl_certificate_key …

  client_max_body_size 7m;   # schema uploads accept up to 6 MiB JSON bodies

  location /api/ { proxy_pass http://127.0.0.1:3000; include /etc/nginx/mockvl_proxy.conf; }
  location /m/   { proxy_pass http://127.0.0.1:3000; include /etc/nginx/mockvl_proxy.conf; }

  location /admin/ {
    root /srv/mockvl;                    # files live in /srv/mockvl/admin/
    try_files $uri /admin/index.html;
  }

  location / {
    root /srv/mockvl/ui;
    try_files $uri /index.html;
  }
}
```

`/etc/nginx/mockvl_proxy.conf`:

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

### 5. Update Google OAuth for production

In the same OAuth client, add:

- Authorized JavaScript origin: `https://mockvl.example.com`
- Authorized redirect URI: `https://mockvl.example.com/api/admin/auth/google/callback`

To serve mocks from a separate origin, set `MOCK_PUBLIC_BASE_URL` (for example `https://mocks.example.com/m`) and route that host's `/m/*` to the API. The app's own origin is always allowed to call mocks for the in-app request preview.

### Optional: docs site

`bun run docs:build` writes a static site to `apps/docs/dist`; any static host can serve it.

## Development

```sh
bun run typecheck          # API + docs
bun run lint               # Biome
bun run test:unit          # no services needed
bun run test               # full suite; needs `docker compose up -d` (uses a separate app_test database)
bun run db:generate        # new migration after editing apps/api/src/db/schema
bun run openapi:dump       # refresh apps/ui/openapi.json, then: bun run --cwd apps/ui openapi-ts && bun run --cwd apps/admin client:generate
```

Admin checks: `bun run --cwd apps/admin tsc && bun run --cwd apps/admin biome:lint && bun run --cwd apps/admin test`. App checks: `bun run --cwd apps/ui lint`.

CI (`.github/workflows/`, path-filtered) runs on pushes to `main` and on pull requests:

- `ci.yml` runs typecheck, lint and tests against Postgres and Redis service containers, builds the Docker image, and smoke-tests it.
- `admin.yml` builds and tests the admin dashboard.

The developer documentation (architecture, conventions, the module pattern, the admin resource registry, background jobs, Redis, testing, the env reference and troubleshooting) lives in the docs site: run `bun run docs:dev`.

**Contributing:** open an issue or pull request. Before you submit, run `bun run typecheck && bun run lint && bun run test`.
